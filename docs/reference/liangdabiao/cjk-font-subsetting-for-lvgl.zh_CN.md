# 为 LVGL 裁剪中文字库子集

做[三字经儿童学习游戏](sanzijing-kids-game/README.zh_CN.md)（一个全离线中文小游戏）时攒下的经验。凡是界面上要显示中文的 AI Passport 应用都适用；下面所有数字都是在 8 MB Flash、无 PSRAM 的 ESP32-C3 上实测的。

## 为什么一定要裁子集

LVGL 自带 Montserrat，但它只有拉丁字母；另有一个默认关闭的思源黑体子集。把一个中文字符串设到字库不含该字的控件上，**不会报错**——标签只是不显示，或者画出一堆豆腐块。LVGL 没有字体回退链，所以**每一个显示中文的控件都必须显式指定一个含这些字的字库**。

对于一本《三字经》游戏来说，需要用到的汉字大约 700 个，所以字库必须裁。本项目三档子集一共覆盖 **785 个码点**。

## 字表要推导出来，不要手写

手维护的字符清单，在有人新增一个菜单文案的那一刻就过期了，而且失败是静默的。正确做法是把三个来源取并集，自动生成：

1. **经文正文的全部字符**，取自构建流程本来就当作唯一事实来源的文本文件。读取时要**先去掉所有空白再逐个取字符**——按空白切分会得到一串"三字字符串"而不是单个汉字，剪出来的子集里会一个汉字都没有。
2. **应用源码字符串字面量里的全部非 ASCII 字符**。扫描前先剥掉 `//` 与 `/* */` 注释，这样中文注释就不占 Flash；字符串字面量要原样保留，包括转义序列。
3. **可打印 ASCII**，以及界面自己会画出来的中文标点与符号：`，。！？、：；（）「」《》…—·""''★☆`。星星符号尤其要注意——用文本拼出来的五星评价，是要吃星形字形的。

这样得到 785 个码点：668 个汉字，117 个来自另外两组。把它写进仓库里的 `charset.txt`，评审的人有东西可 diff，后来的人也能看出**某个字为什么在里面**。

## 转换之前先核对覆盖

这是性价比最高的一步：加载母字体的字符映射，把字表里每个码点都对一遍，有缺就直接让构建失败。

```python
from fontTools.ttLib import TTFont

font = TTFont(source_font, fontNumber=0, lazy=True)
cmap: set[int] = set()
for table in font["cmap"].tables:
    cmap |= set(table.cmap.keys())
missing = [c for c in chars if ord(c) not in cmap]
```

这一步之所以必要，是因为扩充版的经文里有生僻字。本项目遇到的硬骨头包括 籝、膺、悌、菽、匏、曷、橐、灏、韫、缌、碁。把一个字体里没有的字交给转换器，它**不一定**会停——它可能照样产出一份缺这个字的字库，然后你要到真机上、在一课的中间，发现那里是一个空白方块。事先核对，就能把它变成一条带出错字符的构建错误。Noto Sans CJK SC 把这 785 个全数覆盖了。

## 转换时把字符集当字面量字符串传进去

字表要作为一整个字面量字符串从 `--symbols` 传进去，而不是写区间。写区间会拖进成千上万个用不到的字，而裁剪的全部意义就是只为显示出来的字付钱。

```bash
lv_font_conv \
  --font NotoSansCJKsc-Regular.otf \
  --symbols "$(字表去掉注释后连成一串)" \
  --size 24 --bpp 4 \
  --format lvgl --no-compress \
  --lv-include lvgl.h \
  --lv-font-name szj_font_24 \
  -o assets/fonts/szj_font_24.c
```

几个值得说明的选择：

- **4 bpp。** 用 1 bpp 的话，16 px 的汉字会糊成一团——笔画根本表达不出来。4 bpp 是小字号还能看清的临界点；8 bpp 会让 Flash 翻倍，而在这块屏上肉眼看不出提升。
- **`--no-compress`。** 未压缩的点阵留在 Flash 里被内存映射直读，既不需要 `CONFIG_LV_USE_FONT_COMPRESSED`，也不需要解压缓冲。在没有 PSRAM 的芯片上，这个交易更划算。
- **锁死转换器版本。** 本项目用 `lv_font_conv` 1.5.3；生成数据的形状在不同版本之间会变。
- **输出名带上字号**（`szj_font_16`、`szj_font_24`、`szj_font_32`），这样控件的声明本身就说清了用的是哪一档。

## 打开「大字体」格式

32 px 这一档的点阵约 316 KB，而 LVGL 默认文本格式字库里，每个字形的位图偏移量是用 16 位存的。点阵数据一旦超过 64 KB 就会溢出这个字段。生成器产出的 `.bitmap_index` 远超 65535，所以这一项是必须的：

```text
CONFIG_LV_FONT_FMT_TXT_LARGE=y
```

它把这个偏移字段换成 32 位。不开的话，字库要么编不过，要么渲染出乱码——而且症状很有迷惑性，所以每当一份大尺寸生成字库行为异常，先查这个开关。

## 搞清楚它到底花多少

在构建产物上实测（每档 785 个字形）：

| 档位 | 点阵数据 | 生成的 C 源码 |
| --- | --- | --- |
| 16 px | 83,825 字节 | 622,464 字节 |
| 24 px | 184,397 字节 | 1,218,920 字节 |
| 32 px | 316,378 字节 | 2,004,704 字节 |
| **合计** | **584,600 字节（571 KB）** | **3,846,088 字节（3.67 MB）** |

两条教训：

- **`.c` 文件体积不等于 Flash 占用。** 十六进制字面量大约每 1 字节点阵要花 6 字节源码；照着目录列表估预算会差六倍以上。
- **整个 `.rodata` 段是 744,004 字节**，其中点阵占 584,600。剩下的是字形描述符、字符映射表和其它只读数据。要按段做预算，不能只算点阵。

在这块板子上这是付得起的：应用镜像 1,348,800 字节，分区有 8,323,072 字节；而 `.rodata` 是从 Flash 直读的，所以字库**不占 RAM**。DRAM 用量停在 46%。

## 声明与使用

```c
LV_FONT_DECLARE(szj_font_16);
LV_FONT_DECLARE(szj_font_24);
LV_FONT_DECLARE(szj_font_32);
```

三档在界面头文件里声明一次，然后给**每一个**文本控件设字体——包括那些先建成空、之后再填内容的。生成的源码文件要加一行注释说明"这是生成物、怎么重新生成"：它们大到没人会去读，又小到让人忍不住手改。

## 母字体不要进仓库

母字体 OTF 有 16 MB，不该待在一个固件仓库里。生成器按需从固定 URL 下载，并且**校验 SHA-256** 后才使用，这样上游文件变了会直接报错，而不是悄悄改变渲染出来的字形。把字库名称、许可（SIL Open Font License 1.1）和转换器版本，连同生成文件一起记在 `assets/README.md` 里。

## 检查清单

- 字表由经文、界面字符串字面量和符号清单三者推导而来，不是手写的。
- 扫描字面量前已剥掉注释，注释掉的中文不会被带进固件。
- 每个码点都对着母字体的字符映射核过，缺一个字就构建失败。
- 任一份子集的点阵超过 64 KB 时，`CONFIG_LV_FONT_FMT_TXT_LARGE=y` 已打开。
- 预算取自 map 文件或体积报告，而不是生成的源码文件大小。
- 母字体按固定 URL + 哈希下载，不进仓库。
