# 让字库度量决定版式

在[侨批填字问答](qiaopi-quiz/README.md)里攒下的经验。那个应用里所有的版式 bug 都出自
同一个习惯：先给行高挑个整数，先把文案写好，然后才发现字库不同意。这篇讲的是替代
「凭感觉」的那套算术，以及它逼出来的几个决定。

## 先量字库，再摆东西

三档子集由同一份母字体生成，字号 16 / 24 / 32 px。它们的度量是从字库里读出来的，
不是假设的：

| 字号 | 行高 | 一个汉字的前进宽度 |
| --- | --- | --- |
| 16 px | 20 | 16.000 |
| 24 px | 29 | 24.000 |
| 32 px | 38 | 32.000 |

两个后果，都是承重的：

- **一行中文的宽度就是 `字数 × 字号`，分毫不差。** 每个汉字的前进宽度都等于字号，
  所以「210px 里放得下几个字」是一道除法，不是主观判断：32px 是 6 个，24px 是 8 个，
  16px 是 13 个。正因如此，内容上限才能在生成期被卡住，而不是只在设备上看得见。
- **行高不等于字号。** 给 24px 的字配一行 24px 高，字根本没有余地：这一档需要 29。
  本应用里每一行都是 36px 高 —— 29 加两侧各 3px 边框再加 1px 余量，也只有这么多，
  因为四行 36px 加三个 4px 间隔是 156px，而答题页还得在这之上、248px 之内放下句子的
  三行（87px）。

## 同一句话的两种形态，两种都要上限

答题页只能显示那个空，所以它渲染的是把空换成一个槽位之后的句子。判卷页显示的是把答案
填进去之后的句子。两者长度不同，而**槽位形态更长** —— 这跟直觉相反，因为读内容时
你脑子里想的是填好之后的样子。

两种上限都被卡住，生成器卡一次，宿主测试再拿整本真题库卡一次：

| 形态 | 上限 | 实际最长 |
| --- | --- | --- |
| 槽位（答题页） | 22 字 | 22 |
| 已填空（判卷页） | 21 字 | 19 |

## 折行缓冲按最费的调用方开，不按平均

折好的文本写进一个各层共用的模块级静态缓冲，所以它必须装得下最费的那个调用方 ——
上限 60 字、最多折成八行的解析：

```
60 字 x 3 字节          = 180 字节
断点前移带来的换行，最坏 10 个 =  10 字节
结尾 NUL                =   1 字节
                          ----------
                          191 字节   ->   QPQ_WRAP_CAPACITY = 208
```

按句子去估（22 字、3 行、66 字节）看着也够，然后在第一条长解析被折行时溢出。这笔推导
就写在常量旁边，字符和字节都写清楚，让人能复核而不是只能相信。

## 每个 `snprintf` 缓冲区按最宽的转换形态开，并写明理由

GCC 检查 `snprintf` 缓冲区时，是按 `%d` **最宽**的形态算的 —— 含符号 11 个字符 ——
而不是计数器实际会有的那两三位数。对中文界面尤其容易算错，因为每个汉字在任何数字
出现之前就已经占了 3 个字节。本项目的规矩是：

- **按类型的最坏情况开，并把算术写在注释里**，免得后来的人照着观察到的取值范围把它
  「优化」小。
- **失败时写零缓冲区是这份契约的另一半**：折行函数容量不足时返回 0 并把 out 置空串，
  而不是留下一行半截文本 —— 于是缓冲区开小了表现为少一行，而不是花掉的内容。

本项目的固件构建**没有**开 `-Werror=format-truncation`，所以过小的缓冲区只是一条会被
刷过去的告警、不会中断构建。真正可靠的检查是那笔算术，不是编译器。

## 把生成的预算钉在编译期

每行字数出现在三个必须一致的地方：`tools/qiaopi/content.py` 的内容上限、
`main/qpq_text.h` 里生成的宏、以及 `main/qpq_ui.h` 里的版式常量。`qpq_ui.c` 不靠
信任，而是断言它们的关系：

```c
_Static_assert(QPQ_CHARS_BODY * 24 <= QPQ_BODY_W, "24px 每行字数不再放得下");
_Static_assert(QPQ_OPTION_MAX_CHARS <= QPQ_CHARS_BODY,
               "候选要在一行内放得下");
_Static_assert(QPQ_EXPLAIN_MAX_CHARS * 3 + 10 + 1 <= QPQ_WRAP_CAPACITY,
               "折行缓冲装不下最长的解析文案");
```

现在把内容区改窄、或者把某个内容上限调高，会直接编译不过，而不是把文字挤出面板
底部 —— 那地方要等设备到了用户手里才会有人看。

## 页面预算集中写在一处

页面几何是固定的，并且被写下来，好让下一个人能拿新页面直接对它，而不是靠试错发现
约束：

```
页面卡 230 x 310，内缩 5，圆角 25
  顶栏    0 .. 36     (QPQ_BAR_H)
  正文   36 .. 284    (QPQ_BODY_H = 248)
  底栏  284 .. 310    (QPQ_HINT_H = 26)
  内容 x 10 .. 220    (QPQ_BODY_W = 210)

答题页（正文高 248px）
  句子    0 .. 87     24px，3 行 x 29
  候选   92 .. 248    4 行 x 36 + 3 个间隔 x 4 = 156

判卷页
  全部放进唯一那个可滚动容器里的纵向 flex 列里，因为解析 + 完整原文 + 出处
  装不进 248px，而把它们裁掉就等于去掉了当初选这份内容的理由
```

答题页正好是 248px —— 这正是重点：这些数字是解出来的，不是事后凑上去的。

## 纵向预算同样要断言 —— 以及「能滚」不等于「滚得到」

上面那些断言管的都是**宽度**。纵向预算只写在注释里、没有别处约束，而第一次真机测试
抓到的两处缺陷都出自这个缺口：

1. **一个没有任何键能滚动的可滚动容器。** 判卷页比一屏高，是全应用唯一的可滚动对象。
   但它的按键处理把所有按键都转给了状态机，而状态机在判卷阶段只认确定键 —— 上下键
   返回「无动作」，被直接丢掉。在设备上，读者能看到对错与正确答案，**永远看不到解析、
   完整原文与出处**。把它做成可滚动，不等于把它做成够得着：**每一块可滚动区域都要有
   一个键能移动它**，检查方法就一句话 —— 这块区域在屏幕上时，三个物理键各自做什么？
2. **一行被放在正文区之下。** 标题页的成绩标签放在 y = 250，而正文区只有 248px 高。
   LVGL 默认把子对象裁剪在父对象内，于是这一行在设备上根本不存在。而且看起来完全不像
   坏了 —— 少一行「已见 12/91 · 最好 240 分」不像是缺陷。这类问题**在评审里看不见、
   在屏幕上也看不见**。

现在每一页都断言自己的纵向预算：

```c
#define TITLE_MENU_END \
    (TITLE_MENU_Y + (TITLE_ITEMS - 1) * (QPQ_ROW_H + QPQ_ROW_GAP) + QPQ_ROW_H)
_Static_assert(TITLE_MENU_END <= QPQ_BODY_H, "菜单最后一行会被裁掉");
_Static_assert(TITLE_STATS_Y + TITLE_STATS_H <= QPQ_BODY_H, "成绩行会被裁掉");
_Static_assert(TITLE_STATS_Y + TITLE_STATS_H <= TITLE_MENU_Y, "成绩行与菜单重叠");
```

宿主测试覆盖不了这件事：这些常量住在 `include` 了 `lvgl.h` 的文件里。编译期断言是唯一
「不花钱就一直生效」的机制。而成绩行那处的修法是把**它移进**一句与顶栏重复的装饰性副标题
让出的位置 —— 于是断言过了，而且什么都没缩小。
