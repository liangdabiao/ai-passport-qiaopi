# 让字库度量决定版式

同样是在做[三字经儿童学习游戏](sanzijing-kids-game/README.zh_CN.md)时攒下的经验。那个应用里所有的版式 bug，都出自同一个习惯：先给行高挑个整数，先把文案写好，然后才发现字库不同意。这篇讲的是替代"凭感觉"的那套算术，以及它抓出来的三个真实缺陷。

## 一行的可用高度不等于它的高度

带 3 px 边框的列表行，文字拿不到整行的高度——边框从两边各吃掉一条：

```text
可用文字高度 = 行高 - 2 * 边框宽度
```

这个值必须不小于字库的 `line_height`。本项目三档子集在 LVGL 里报出来是：

| 字库 | `line_height` |
| --- | --- |
| `szj_font_16` | 20 px |
| `szj_font_24` | 29 px |
| `szj_font_32` | 38 px |

注意 `line_height` 明显大于名义字号：24 px 的字库要 29 px，32 px 的要 38 px。**坑就在这里。** 40 px 的行减去 3 px 边框还剩 34 px 内容区，看上去装"24 px 的字"绰绰有余——确实绰绰有余。但同一个 40 px 的行拿来放 32 px 的选项时，34 px 对 38 px 的需求就不够了，字形上下各被切掉 2 px。这在真机上看得到，在源码里看不出来。

所以顺序要反过来：**先定字库，再解出行高。**

```text
行高 >= line_height + 2 * 边框宽度
```

落到最后是这样：

| 行 | 改前 | 改后 | 原因 |
| --- | --- | --- | --- |
| 首页菜单行（24 px 字） | 34 | **36** | 34 只剩 28 px，需要 29 |
| 闯关选项行（32 px 字） | 40 | **46** | 40 只剩 34 px，需要 38 |
| 设置行（24 px 字） | 40 | 40 | 本来就够 |

选项行拔高 6 px，就意味着上面的题面面板得让出 16 px（76 改成 60），整页才装得下。这是常态：在 240 × 320 的屏上，把某一行改高，整页的竖向预算都要重算。

## 把竖向账算出来，写在注释里

现在每个页面的常量旁边都写着它的竖向预算，加起来一眼能核：

```text
首页（页面卡 310 px 高，底栏从 284 开始）
  顶栏       0 .. 36
  招牌      44 .. 110
  菜单     118 .. 280    4 行 x 36 + 3 个间隔 x 6 = 162
  底栏     284 .. 310

闯关（内容容器 248 px 高）
  题号       6 .. 26
  题面      32 .. 92
  选项      96 .. 242    3 行 x 46 + 2 个间隔 x 4
  底部余量              6
```

写代码之前先把这笔账写出来。页面溢出**不会优雅地裁掉**——最后一行直接从屏幕底部消失，而在一个没有滚动视图的设备上，用户没有任何办法把它够回来。

## 拿真实字库量文字宽度

LVGL 排一个标签，是把字形的前进宽度逐个相加、不做字距调整，所以宽度可以直接从字体文件算出来。把前进宽度求和再按像素尺寸缩放，得到的就是设备上会用的那个数：

```python
from fontTools.ttLib import TTFont

font = TTFont("NotoSansCJKsc-Regular.otf", lazy=True)
upem = font["head"].unitsPerEm
cmap = font.getBestCmap()
hmtx = font["hmtx"]

def width(text, px):
    return sum(hmtx[cmap[ord(ch)]][0] for ch in text) * px / upem
```

**在写界面之前**，把界面上每一条文案都过一遍这个函数，和各处的可用宽度比。这个检查抓到过一次实打实的撞车：设置页那行文案——六个汉字，意思是"重置学习进度"——在 24 px 下宽 144 px，而那一行的主文字区只有 124 px。这一行宽 210 px，减掉两边各 3 px 边框、各 8 px 内边距，再减掉留给右侧状态字的 64 px，就只剩这么多。文案会直接压到状态字上。改成四个字（"重置进度"）后解决了。

中文在这里反而**特别好算**：24 px 档的四个字就是正好 96 px，因为汉字是全角的。同一个界面里的英文串完全不遵守这条规律——所以度量必须逐条文案做，不能按字符数估。

## 格式化缓冲区按最坏情况开，不按实际情况开

有两处 `snprintf` 以 `-Werror=format-truncation` 挂了构建。缓冲区看着对实际取值是够的，而这恰恰是问题所在：GCC 是拿缓冲区去对**最宽的** `%d` 做检查——含符号位 11 个字符——而不是计数器实际上会有的两三位。

题号标签是这么拼的：

```c
char caption[16];   // 太小
snprintf(caption, sizeof(caption), QUESTION_FORMAT, index + 1, total);
```

这个格式串有 9 个字节的字面文本（两个各 3 字节的汉字，加空格和斜杠）和两个整数转换。最坏情况是 `9 + 11 + 11 = 31` 字节文本再加结束符：32。16 字节的缓冲区差得远。

本项目采用的修法，是**按类型的最坏情况开缓冲区，并在注释里写明原因**，免得以后有人又"优化"回实际取值范围：

```c
// 缓冲区按 int 的最坏十进制宽度取,别按实际题数取 —— 实际最多 6 题,
// 但 GCC 的 -Wformat-truncation 只认类型范围,按实际值开数组会报截断错误。
char caption[48];
snprintf(caption, sizeof(caption), QUESTION_FORMAT, index + 1, total);
```

另一种做法是**把数值夹住**，适用于缓冲区必须很小的场合——那样标签会停在 999 而不是被切断，对用户更友好——但同样需要写一句"这是故意的"注释。

中文文案比英文更容易撞上这条，因为每个汉字在任何数字出现之前就已经花掉 3 个字节了。所以要把应用里所有 `snprintf` **一次性全过一遍**，不要跟着编译错误一个一个修。

## 顺带一条：字符数不是字节数

这是另一个缺陷，但属于同一族——**算文字时用错了单位**。认字卡页面把一课 12 个字拆成两行六字来显示。代码把一行算成"每字 3 字节 × 4 句 = 12 字节"，于是每行拷 12 字节——可这只能盖住一课的 8 个字（12 字节 = 4 个字，4 × 2 = 8）。**结果就是每一课的第 4 句从来没显示出来过。**

修法是每行 18 字节（6 个字 × 3），再加一条编译期约束，让这个关系不会再漂走：

```c
_Static_assert(CARD_HALF_BYTES * CARD_HALF_COUNT ==
                   (SZJ_LINE_BYTES - 1) * SZJ_LINES_PER_STANZA,
               "认字卡两行必须正好覆盖一整课的字节数");
```

`SZJ_LINE_BYTES - 1` 是一句正文去掉结束符的字节数，于是等号右边是一课正文的 36 个字符字节，等号左边是"每行的字节数 × 一共几行"。

"格数"和"字节数"是两种东西。在源码里把它们**用不同的名字区分开**——`CARD_GLYPH_BYTES` 表示一个汉字占几字节，`CARD_CELL_COUNT` 表示一格能放几个字——才是真正避免混淆的做法。

## 检查清单

- 行高由 `line_height + 2 * 边框` 推出来，不是挑的整数。
- 每个页面都有一份写下来的竖向预算，各部分相加等于页高。
- 每一条用户可见的文案，在写代码之前都量过可用宽度。
- 每个 `snprintf` 缓冲区都按最宽的转换结果开，并在注释里说明原因。
- 会长大的标签用固定宽度并省略号截断。
- 任何把字符、字节、格数混在一起的算术，都用编译期断言兜住。
