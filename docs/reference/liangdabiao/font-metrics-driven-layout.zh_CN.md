# 让字库度量决定版式

同样是在做[侨批填字问答](qiaopi-quiz/README.zh_CN.md)时攒下的经验。那个应用里所有的版式 bug 都出自同一个习惯：先给行高挑个整数，先把文案写好，然后才发现字库不同意。这篇讲的是替代「凭感觉」的那套算术，以及它抓出来的几个真实决定。

## 一行的可用高度不等于它的高度

带 3px 边框的列表行，文字拿不到整行高度——边框从两边各吃掉一点：

```text
可用文字高度 = 行高 - 2 × 边框宽
```

这个值必须不小于字库的 `line_height`。本项目三档子集，LVGL 报出来的是：

| 字库 | `line_height` |
| --- | --- |
| `qpq_font_16` | 20 px |
| `qpq_font_24` | 29 px |
| `qpq_font_32` | 38 px |

注意 `line_height` 明显大于标称字号：24px 字库要 29px，32px 要 38px。这就是陷阱所在。一个 40px 行、3px 边框，内容区剩 34px，看着放「24px 的字」绰绰有余——确实够。但同一个 40px 行如果放 32px 的字，34px 对上 38px 的需求，上下各被裁掉 2px。这在真机上一眼能看见，在源码里却看不见。

所以顺序是：**先定字号，再解行高。**

```text
行高 >= line_height + 2 × 边框宽
```

落到本项目的三个行：

| 行 | 字库 | 行高 | 边框 | 可用 | `line_height` |
| --- | --- | --- | --- | --- | --- |
| 列表行（`QPQ_ROW_H`） | 24 px | 44 | 3 | 38 | 29 |
| 首页菜单行 | 24 px | 44 | 3 | 38 | 29 |
| 设置行 | 24 px | 44 | 3 | 38 | 29 |

44 不是为了好看的整数。24px 字库只要 29px 可用高度，所以 40 本来也够；但 44 让可用高度变成 38px，正好是 32px 字库需要的数。多出来的那 4px 只买一件事：**改字号那天，这个共享行高还能用，四个页面的垂直预算不用重算。** 一次性花在一个常量上，比等到某个标签长大的那天再把每个页面的预算重推一遍便宜。

## 把页面的垂直预算写出来，让各项加起来等于页高

每个页面的常量旁边都带着它的垂直预算注释，加起来对不对一眼可查。页面卡是 230 × 310、内缩 5px，内容列从 10px 起、宽 210px：

```text
页面卡  230 × 310，内缩 5，圆角 25
  顶栏       0 ..  36      (QPQ_BAR_H)
  主体      36 .. 284      (QPQ_BODY_H = 248)
  底栏     284 .. 310      (QPQ_HINT_H = 26)
  内容 x    10 .. 220      (QPQ_BODY_W = 210)

首页
  小字      38 ..  58
  菜单      64 .. 258      4 行 × 44 + 3 个间隙 × 6 = 194

日课·原文层（主体 248 高）
  小标签          y = 2
  原文      24 .. 248      DAILY_READ_H = 248 - 24 = 224

日课·参究层
  小标签          y = 2
  提问      22 ..  90      DAILY_QUESTION_H = 68
  选项      96 .. 244      3 行 × 44 + 2 个间隙 × 8 = 148
```

写代码之前先把这段列出来。溢出**不会**优雅裁切——最后一行就是凭空消失在屏幕下方，而在一个没有滚动视图的设备上，读者没有任何办法够到它。上面这段数字里有两个结论：

- **原文层没有自己的小标签**（只留 2px 偏移）。一份小标签要的 20px，正好是「5 行原文」和「4 行原文」的差别。进度改到底部提示条里报告，那里本来就在屏幕上。
- **只有章节列表会拿到可滚动容器**（目录页与待参页），因为列表天生就超出屏幕。其它层全部是静态排布、必须被证明放得下——这正是这套预算值得写下来的原因。把可滚动对象收敛到一个控件，也意味着「意外触发的滚动」只有一个地方可能发生。

## 把「每行几个字」做成一次除法，并且在两处同时钉住

内容列宽 210px。因为每个全角汉字的步进**精确等于**字号（证明见字库子集那篇），「一行放得下几个字」就是一次除法，而且代码里就写成除法：

```c
#define QPQ_CHARS_PASSAGE (QPQ_BODY_W / 32)   // 6
#define QPQ_CHARS_PARA    (QPQ_BODY_W / 24)   // 8
#define QPQ_CHARS_NOTE    (QPQ_BODY_W / 16)   // 13
```

写成除法而不是直接写 `#define QPQ_CHARS_PASSAGE 6`，好处不只是「内容区一改数字自动跟着改」，而是它可以被编译期断言：

```c
_Static_assert(QPQ_CHARS_PASSAGE * 32 <= QPQ_BODY_W, "原文每行字数不再放得下");
_Static_assert(QPQ_CHARS_PARA    * 24 <= QPQ_BODY_W, "点拨每行字数不再放得下");
_Static_assert(QPQ_CHARS_NOTE    * 16 <= QPQ_BODY_W, "提示每行字数不再放得下");
```

这样的数字应该存在三份对应关系。同一个上限也在生成侧声明了一遍，位于 `tools/qiaopi/content.py`，用来卡掉「长到一屏放不下」的章节。两边必须一致：只留一边的话，章节能过生成、然后在屏上溢出。在这之上，`tests/test_qpq_wrap.c` 直接连**真实经文**，断言折行后的任何一行都不超过每行上限——于是这个上限在生成期、编译期和主机测试里各被守了一次。

## 拿真字库量文案宽度

LVGL 排标签就是把字形步进加起来、不做字距调整，所以宽度可以从字库文件精确预测。把步进加起来、按像素尺寸缩放，得到的就是设备会用的那个数：

```python
from fontTools.ttLib import TTFont

font = TTFont("NotoSansCJKsc-Regular.otf", lazy=True)
upem = font["head"].unitsPerEm
cmap = font.getBestCmap()
hmtx = font["hmtx"]

def width(text, px):
    return sum(hmtx[cmap[ord(ch)]][0] for ch in text) * px / upem
```

把它跑过**界面上的每一条文案**，逐条对着它拥有的空间比一遍。这一步在目录页换来了一个真实的设计决定。列表行宽 210px，它的主文字区是：

```text
210 - 2 × 3（边框） - 2 × 8（内边距） - 88（右侧注释位） = 100 px
```

24px 字下这就是 4 个字。最顺手的标题写法是「章号 + 章题」——六个汉字 144px，超了 44px，于是两半都会被省略号截掉，读者看到的是一个没有标题的章号。所以章号被挪进了右侧那个 16px 字的注释位（88px 宽，够放 5 个字），绰绰有余。`main/qpq_catalog.c` 顶部的注释记下了这笔算术，后来的人不用重新推一遍，也不会把它改回去。

中文在这一点上出奇地可预测：24px 子集的四个字**正好** 96px，因为汉字是全角。同界面里的拉丁字符串完全不遵守这条，所以量宽度必须逐条做，不能按字数估。

## 格式化缓冲区要按最坏情况开，不是按真实情况

GCC 检查 `snprintf` 的缓冲区时，用的是 `%d` 的**最宽可能形态**——含符号位 11 个字符——而不是计数器实际会装的两位或三位。对中文界面这尤其容易踩，因为任何数字出现之前，每个汉字已经先花了 3 个字节。底部提示条那条格式是：

```c
char foot[64];
snprintf(foot, sizeof(foot), "日课 %d 次 · 已读 %d/%d 章", sessions, read, total);
```

```text
字面量           27 字节   （6 个汉字、各处分隔符与那个斜杠）
3 × 最宽 %d      33 字节   （每个 11 字节，含符号位）
               --------
最坏情况         60 字节
+ 结尾符         61 字节
```

最坏情况是 `60` 字节文本，加上结尾符 61。若按真实值来估（「第 3 次、91 题里的第 1 章」），会得出 16 字节就够的结论——差了四倍。另外注意那个间隔点（U+00B7）在 UTF-8 里是 **2 字节**，既不是 1 也不是 3；按字符数去估这段字面量，两个方向都会算错。本项目的规矩是：

- **按类型的最坏情况开，并在注释里说明原因**，免得后来的人照着真实取值范围把它「优化」小。而且那笔算术要写在声明旁边——单看声明，一个从不超过两位数的计数器配 24 字节缓冲区实在荒谬。
- **缓冲区必须保持很小时，夹取是替代方案**——标签会停在 999 而不是被截断，对用户更友好——但同样需要那句「这是有意的」注释。
- **`%s` 需要另一套论证，而且必须把论证写出来。** 对 `"%s · %s"` 来说没有「最宽可能的转换」，它的边界来自两个实参**取自封闭集合**——卷名恒为两个字，章号文案最多五个字。这个论证也得写下来；「反正是字符串、肯定放得下」正是那个放不下的缓冲区被写出来的方式。本项目所有 `%s` 都来自封闭集合，每一处都写明了是哪个集合。

把应用里每一处 `snprintf` 一次性按这个模式扫一遍，别等一条条编译错误来找你。本项目的固件构建**没有**开 `-Werror=format-truncation`，所以过小的缓冲区只是一条会被刷过去的告警、不会中断构建；真正可靠的检查是那笔算术，不是编译器。做这次清扫有个好办法：写个二十行的小脚本扫源码，取出每一条字面量格式串，每个整数转换代 11 字节，加上字面量的 UTF-8 宽度，与声明的尺寸比对。就是这么个小脚本，在本项目里找出了三个按真实值而不是按类型取值范围开的缓冲区。

## 还有一条：字符数不是字节数

这是另一个缺陷，但同属一族——关于文本的算术用错了单位。UTF-8 下一个汉字是 3 字节，所以一个按「字符」开、按「字节」填的缓冲区会短三倍。本项目有两处必须同时持有两种单位，都给**单位起了名字**，而不是靠人小心：

```c
#define QPQ_PASSAGE_MAX_CHARS 24   /* 字符 —— 版式上限 */
#define QPQ_POINT_MAX_CHARS   48   /* 字符 —— 版式上限 */

/* 字节 —— 缓冲区必须装得下两者中更大的那个 */
#define QPQ_WRAP_CAPACITY 176
```

折行缓冲区是最有说服力的一个。折好的文本写进一个三处共用的模块级静态缓冲区，所以它必须按**最长的调用者**开——是解析（60 字），不是原文（22 字）：

```text
48 字按 8 字一行         = 6 行
                        = 5 个插入的换行
48 字 × 3 字节           = 144 字节文本
144 + 5 个换行           = 149 字节
+ 结尾符                 = 150 字节
```

`QPQ_WRAP_CAPACITY` 是 208，留 17 字节余量。要是按句子估（22 字、3 行、66 字节），看着也够——然后在第一条六行的点拨被折行时溢出。这笔推导就写在常量旁边，字符和字节都写清楚，让人能复核而不是只能相信。

这也解释了为什么折行函数的契约必须交代边界行为：它只在行**之间**插换行、绝不加尾换行，所以换行数等于 `行数 - 1`——正是这一点让上面那笔算术闭合。若它改成追加尾换行，换行数变成 6，同一个容量依然够用，但注释里那个数字就是错的；而一笔算不闭合的注释，比没有注释更糟。

同一个区分也解释了存档格式的常量为什么写成字节数、并把算术摊开：`4 个头字节 + 81 个章位 + 2 × 11 个错题字节 + 1 个校验字节 = 108`，并在主机测试里对 `QPQ_PROGRESS_BLOB_SIZE` 断言。槽位数和字节数是两回事；在源码里给它们起不同的名字，才是防止混淆的那一步。

## 检查清单

- 行高由 `line_height + 2 × 边框` 反解而来，不是挑的整数。
- 每个页面都有写出来的垂直预算，各项之和等于页高。
- 每行字数上限写成内容区宽的除法，并用 `_Static_assert` 钉住。
- 同一个上限在生成侧也声明了一遍，内容在溢出到屏上之前就被拒掉。
- 每条用户可见文案都在写代码之前量过可用宽度，量出来的决定记进了注释。
- 每个 `snprintf` 缓冲区都按最宽的转换形态开，并注释说明它为什么比看起来需要的更大；实参是 `%s` 的地方，注释里写明它来自哪个封闭集合。
- 需要装 UTF-8 文本的缓冲区按字节开，依据是写出来的字符到字节推导，命名上也看得出单位。
