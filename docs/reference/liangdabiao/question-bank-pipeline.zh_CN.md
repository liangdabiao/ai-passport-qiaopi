# 把章节内容整理成生成的 C 数组

为[侨批填字问答](qiaopi-quiz/README.zh_CN.md)而写。这个应用的全部内容就是一套整理好的章节——已收录 1 章，全书 91 题。这篇讲的是把一章变成固件数据的那条流水线：一章一个源文件、一个对任何畸形输入都拒绝的解析器、一个把源文件投影成 C 表的生成器，以及一个让过期表直接失败构建的 `--check` 模式。

## 问题：一章没有固定形状

固定句式的诵读文本天然给你一层结构保证——每一课行数相同，于是「第 60 课」就是一道算术。道德经不是这样：有的章只有两三句，有的十几句；点拨该多长就多长；而全书是一篇谁都能重打一遍的散文。

两个后果决定了下面所有设计：

- **数据模型是「平铺的表 + 每章一条索引记录」**，而不是「每章一条定长子记录」。生成的表头里有三张独立的表（原文屏、点拨条、参究选项），每章记录只持有指向它们的偏移量与条数。
- **今天 91 题里只有 1 章存在。** 所以流水线的头号任务是让**新增一章**成为唯一需要做的编辑——不碰任何 C 文件、不加任何常量、不改任何测试。

## 一章一个文件，格式刻意做得无聊

章节源文件放在 `tools/qiaopi/chapters/`，一章一个文件，文件名就是章号、补零到三位。格式刻意做得朴素：

```text
# 以 '#' 开头的行是注释，可以出现在任何位置
chapter = 1
volume = 道经          # 两个卷名之一
title = 道可道         # 章题，最好三四个字

[原文]
一行一屏，标点既不添加也不删除

[点拨]
一条一行

[参究]
question = 一行
option   = 正好三条，按槽位顺序
```

四点理由，值得为这个格式坚持：

- **行就是应用计数的单位。** 一屏原文是一行、一条点拨是一屏、一个参究选项是一行。让文件的单位与领域的单位对齐，就消掉了一整层解析。
- **diff 干净。** 评审的人看到的是一行改动，不是一段重排。
- **没有语法可以写错。** 不用引号、不用转义、没有会与内容混淆的分隔符。分节标题是唯一的分隔符，而且只有三个。
- **没有标点是内容，不是偷懒。** 原文的标点本身就是读音的一部分，而折行器的禁则正是照着这几个标点写的。为了「看起来舒服」加一个逗号或删一个，改变的不只是显示，还有折行器看到的东西。

## 三个选项是位置化的，靠格式强制

参究层收在一个提问和三个选项上。三个选项没有对错——它们记录一种倾向：**接了 / 还要想 / 没接上**。待参队列就是从记录下来的倾向推导出来的。

这只有在「槽 0 永远是同一个意思」时才成立。所以格式要求**正好三条**、按槽位顺序，生成器原样输出：

```python
if len(options) != OPTION_SLOTS:
    raise ContentError(
        f"{path.name}: [参究] needs exactly {OPTION_SLOTS} options, got {len(options)}"
    )
```

另一种做法是让每条选项都写成 `键 = 值`，文件更好读，但**顺序即语义**这件事就变成了隐含约定。当顺序本身就是语义时，把它写进语法里是更便宜的交易。

## 所有失败都要响，而且要报出行号

除非源文件满足形状规则，否则解析器不产出任何一章，并且会指明是哪里坏了。它接住的全部情形：

| 失败 | 为什么重要 |
| --- | --- |
| 未知键、未知分节、重复键、缺少键 | 打错一个字本来会被静默忽略，那一章就带着一个默认值上线了。 |
| 文件名与 `chapter =` 不一致 | 文件名差一位是最容易犯、也最难发现的错；第 1 章会显示第 2 章的正文，配上自己的章题。 |
| 章号有断档 | 「下一章是哪章」是从顺序算出来的，一个断档就悄悄把书缩短了。 |
| 卷名与章号不符 | 卷名会在每一屏原文上显示；写错就是在一整章里对读者说假话。 |
| 章题为空 | 目录页和顶栏会显示一个空标签。 |
| 原文、点拨、提问或选项超长 | 运行期会在屏上溢出。 |

报出位置这件事比看起来重要。「期望 48 个字」而不说是哪个文件哪一行，等于要人手工把一章二分——而全书计划 91 题，这恰恰是你最常撞上的失败模式。

## 在生成器里卡住「一屏放得下」

这是整条流水线里最值钱的一条规矩。每个层的字号在屏上放得下固定几个字，所以生成器拒收任何超过一屏的内容：

```python
#   层        字号  每字宽  每行  行数  上限
#   原文       32     32      6     4     24
#   点拨       24     24      8     6     48
#   参究问题   16     16      13    2     26
#   参究选项   24     24      7     1     7
PASSAGE_MAX_CHARS = 24
POINT_MAX_CHARS = 48
QUESTION_MAX_CHARS = 26
OPTION_MAX_CHARS = 7

for index, passage in enumerate(passages):
    if len(passage) > PASSAGE_MAX_CHARS:
        raise ContentError(
            f"{path.name}: passage {index + 1} is {len(passage)} characters, "
            f"over the {PASSAGE_MAX_CHARS}-character limit for one screen; "
            "split it into another screen instead"
        )
```

有两点让它比一份「写作规范」有用得多。第一，报错信息给出的是**修法**——拆成多屏——而不只是「你违规了」。第二，同一批数字在渲染侧也声明了一遍，在 `main/qpq_ui.h` 里写成内容区宽的除法并配 `_Static_assert`；于是改版式会直接编不过，而不是让内容过了生成、再在屏上溢出。

而且这些上限是为那一层的**职责**定的，不只是为尺寸。点拨 48 字不是「能放多少就放多少」——它是「一条点拨还是一条点拨、再长就变成一篇小文章」的那个长度。把上限写下来，是让点拨在第 10 个供稿人之后仍然是bullet 列表的原因。

## 生成 C 表，常量从数据推导

`tools/qiaopi/gen_content.py` 读那些文件，写出 `main/qpq_text.h` 与 `main/qpq_text.c`。值得照抄的一点是：表头里的常量是**从数据算出来的**，不是手写的：

```c
#define QPQ_TOTAL_CHAPTERS 81
#define QPQ_DAO_LAST_CHAPTER 37

#define QPQ_CHAPTER_COUNT 1
#define QPQ_PASSAGE_COUNT 6
#define QPQ_POINT_COUNT 5
#define QPQ_OPTION_COUNT 3
#define QPQ_PONDER_OPTION_COUNT 3
```

`QPQ_TOTAL_CHAPTERS` 是唯一一个**不是**推导出来的常量，这是有意的：全书就是 91 题，收没收录都一样；进度从第一天起就按 91 题存，所以存档格式不会随着收录推进而改变。其余全部——收录了几章、展开多少屏、多少选项——都是从源文件求和得来的。手维护的计数会在有人新增一章的那一刻出错，而失败形态是「某一章悄悄短了一截」。

## 生成物必须说明自己是生成物

两个输出都以一行横幅开头：

```c
// Generated by tools/qiaopi/gen_content.py from tools/qiaopi/chapters/*.txt.
// Do not edit by hand; edit the chapter source and run the generator.
```

`main/qpq_text.c` 是个没人会读的小文件，全是字符串字面量。没有这行横幅，它就是「顺手改一下」的最佳候选——而那次顺手改动会被下一次重新生成静默删掉。

## `--check` 模式：让 CI 抓住过期文件

生成器支持 `--check`：报告已提交的表与源文件是否仍然一致，不写任何东西。

```bash
python3 tools/qiaopi/gen_content.py --check
```

它把「记得重新生成」变成一条规矩。`tools/validate.sh --static` 第一件事就是跑它，排在所有测试之前。没有它，改了章节文件却忘了生成器，会得到一个编译通过、却把旧经文发出去的构建——最糟的那类失败，因为一切看起来都健康。

字库生成器出于同样的理由有同一个开关，也接在同一道门禁上——但只在它需要的工具在位时才跑：

```bash
if python3 -c "import fontTools" >/dev/null 2>&1; then
    PYTHONDONTWRITEBYTECODE=1 python3 tools/qiaopi/gen_font.py --check
else
    echo "skip: gen_font.py --check（无 fontTools；字形清单同步未校验）" >&2
fi
```

核对字形清单需要字符映射表，那需要 `fontTools` 和那份 16 MB 的母字体——两者都不该进 CI 镜像。所以这一步**响亮地跳过**：它会把「这次没校验」打出来，而不是从门禁里悄悄消失，更不是写成「依赖缺失看起来像通过」。一道无法失败的门禁步骤不是检查；一道谎称自己跑过的门禁步骤，比干脆缺席更糟。

## 两个生成器共用一个模块来串联

两个生成器是**设计上**相连的，不是靠约定：它们都 import `tools/qiaopi/content.py`，而后者是唯一读取章节文件的代码。

```text
tools/qiaopi/chapters/*.txt
   └─ content.py         （解析；唯一的事实来源）
        ├─ gen_content.py  ->  main/qpq_text.{c,h}       （数据表）
        └─ gen_font.py     ->  assets/fonts/qpq_font_*.c （字形）
```

因此往一章里加一个字，可能连带需要重新生成字库子集。这是特性而不是成本：字形清单是「章节正文 ∪ 界面文案」，新字会自动被收进来，而不是在某一块屏上渲染成一个空白方块。要是字库生成器自己另写一套解析、直接读章节文件，两边就可能对「经文写了什么」各说各话——而症状会是「某一章少了一个字形」，正好是没人校对的那一章。

两个都跑，然后跑门禁。

## 把不变量测在能快速失败的地方

生成器在生成期校验文本。主机测试则回头复核**生成出来的数据**，这样即使没人跑生成器，过期的提交也会被抓到：

```c
for (int index = 0; index < QPQ_CHAPTER_COUNT; index++) {
    const qpq_chapter_t *chapter = qpq_chapter_at(index);
    assert(chapter->number == index + 1);
    assert(chapter->option_first == (uint16_t)(index * QPQ_PONDER_OPTION_COUNT));
}
assert(passage_sum == QPQ_PASSAGE_COUNT);
assert(QPQ_OPTION_COUNT == QPQ_CHAPTER_COUNT * QPQ_PONDER_OPTION_COUNT);
```

`option_first` 那条一定要留着。每章的三个选项存在一张共享表里，章记录只持有指向它的偏移量。要是某章生成出来的偏移不是 3 的倍数，那一章的三个选项就会**悄悄变成另外三章的答案**。一条关于「生成器输出」的结构规则，恰恰是评审时看不见、写成主机测试却只要几行的东西。

## 内容变更后的固定动作

```bash
# 1. 编辑 tools/qiaopi/chapters/NNN.txt
python3 tools/qiaopi/gen_content.py          # 重新生成 C 表
python3 tools/qiaopi/gen_font.py             # 重新生成字库子集
python3 tools/qiaopi/gen_content.py --check  # 确认没有过期
python3 tools/qiaopi/gen_font.py --check
./tools/validate.sh --static                    # 数据不变量、主机测试
```

## 检查清单

- 一章一个整理好的源文件是文本的唯一事实来源，从不在 C 里直接改。
- 文件格式的单位与领域的单位对齐，没有需要转义的语法。
- 位置化的数据（三个选项）由语法强制，而不是靠注释约定。
- 任何畸形输入都被拒，并报出文件名与行号。
- 屏幕容量上限在生成期卡住，报错信息同时给出修法。
- 同一批上限在渲染侧也声明了一遍，并用 `_Static_assert` 守住。
- 生成器从数据推导每一个计数，不手写。
- 生成物带「勿手改」横幅，并写明生成器是谁。
- 有 `--check` 模式，CI 能抓出过期输出。
- 两个生成器通过同一个共享模块读内容，所以 C 表与字库清单不可能不一致。
- 数据不变量在主机测试里断言，不只留在生成器里。
